## What Seal is
E2EE group chat where friendships require an in-person ceremony: friend taps THEIR FIDO2 hardware key (or passkey via hybrid flow) on YOUR phone; you verify their signature against the CloudKit public directory. Wedge: "everyone is provably human and provably someone you've met" (anti-bot/anti-AI positioning — see docs/VISION.md). Zero servers: CloudKit public DB + one static AASA file.

## Architecture (docs/SDS.md is authoritative)
- Root identity = WebAuthn credential (hardware key "Verified" tier = brass; passkey = silver). Root endorses per-device Secure Enclave P-256 signing key + software X25519 KEM key via assertion whose challenge commits to BOTH keys (`seal.endorse.v2` — binding auth+encryption keys, MITM fix).
- Messages: per-sender chains, HKDF ratchet, AES-GCM; AAD binds group|epoch|sender|index|prev-ciphertext-hash (transcript tamper evidence; epoch 0 = legacy `seal.msg.v2` format, epoch ≥1 = `v3`). Sender chains wrapped to members via X25519 ephemeral-static (ML-KEM hybrid still TODO, spike needed).
- Transport: CloudKit public DB, deterministic record names (no queries except GroupInvite): `msg.<group>[.e<epoch>].<sender>.<idx>`, `kenv.<group>[.e<epoch>].<sender>.<recipient>`. Push = CKQuerySubscription on Message.recipients.
- Groups: signed GroupInvite records (kind nil=invite, "update"=membership change); creator = admin; removal bumps epoch → fresh chains exclude removed member (FR-13 done).
- Revocation (FR-19 done): root-key assertion committing to device pub (`seal.revoke.v1`), stored in Identity.revocations; fetchIdentity filters revoked endorsements.
- Sign-in: assertion w/ empty allowList → directory lookup by credentialID hash → verify vs published pubkey → endorse this device (appended, multi-device-ish; senders wrap to `.last` endorsement). NOTE: security-key sign-in uses the directory's published credentialIDs as the allow-list (non-resident keys find nothing on an empty list). PIN'd-key "wrong PIN" was the `always_uv` vs `.discouraged` conflict — fixed 6/26 by switching to `.preferred` (see Known issues); residentKey stays `.discouraged` for this allow-list design.
- Storage: all local state keychain-JSON namespaced per identity hash (`seal.chats.<hash>` etc.); Sign out wipes local, identity survives in directory.

DONE 8/25 (review round, same session): an adversarial review of the FR-3 code above found a **recovery-hijack hole in the original design, now closed.** `SHA256(backupCredentialID)` is a record name NOBODY EVER CREATES, and a backup key's credential ID goes public the moment it is published — so an attacker could create an Identity record at exactly that name carrying the backup's own public key. A recovering user's tap would verify perfectly (it is genuinely their key) and their phone would adopt the attacker's record as its identity, overwriting the local one. Two fixes: (1) **the statement is now two-sided** — the backup credential signs its own acceptance, `SHA256("seal.backup.accept.v1" + rootIDHash + credentialID + publicKey)`, verified under the BACKUP's key and naming the root, so no identity can claim a credential it doesn't hold and no acceptance can be lifted into another record (costs a third tap when adding: new key creates → new key accepts → root endorses, because registration attestation is a batch-key signature and is not proof of possession of the credential's own key); (2) **sign-in fails closed on a contested credential** — if more than one identity claims the tapped credential the ceremony refuses instead of guessing, and a record is only accepted as an identity if it carries a device endorsement signed by the key it publishes. Also from the same review: `verifiedDevices` now FALLS THROUGH instead of returning when the authority named by `assertion.credentialID` fails (that field is outside the signature, so a directory flip could otherwise silently kill a recovered phone); the local keychain copy of one's own identity is persisted WITHOUT `backupCredentials` (a keychain copy is never re-filtered against revocations, so it would name a revoked backup as an authority forever); the directory-scan fallback now degrades ONLY on `CKError.invalidArguments` (the real schema-gap signal) instead of swallowing network errors and telling a recovering user "no identity matches that key — register instead?"; and the revoke dialog now says that revoking a backup also permanently kills every phone that key set up. **Honest limitation now stated in the UI instead of discovered by tapping: a phone recovered WITH a backup key cannot add another backup or revoke the one it used, because both ceremonies need the root key — that identity is frozen at one credential until the root turns up.** Still UNCOMPILED. **Separately flagged, NOT introduced here and not fixed here — pre-existing and worth their own pass:** `DeviceEndorsement.revokedAt` is an unsigned field that gates verification (anyone who can write a record can un-verify every device on it — no key needed); `seal.endorse.v2` concatenates two variable-length values with no length framing; `WebAuthnAssertion.verify` never checks the RP ID hash, the UP/UV flags or `clientData.type`; `signIn`/`register` publish their endorsement assertion without verifying it first (`addBackupKey` does); `CeremonyManager.signReceipt` will sign ANY caller-supplied bytes with the counterparty's ROOT key, which is a signing oracle if the receipt commitment is ever not domain-prefixed — worth checking before the custody-receipts work lands; and nothing pins a friend's root public key at forge time.

DONE 8/25 (evening): the four pre-existing verification holes from docs/VERIFICATION_HARDENING_PLAN.md, items 1–4. (1) **`DeviceEndorsement.revokedAt` no longer gates verification** — it was an unsigned field, first condition in `verifiedDevices`, so anyone who could write an Identity record could set it on every endorsement and un-verify every device on it with no key and no signature, presenting as an exact replica of the 6/26 desync. The app never wrote a non-nil value; the field only ever served an attacker. Root-signed `revokedDevicePublicKeys` remains the only revocation channel. (2) **`WebAuthnAssertion.verify` now checks the WebAuthn context** — rpIdHash == SHA256(sealmessenger.com), User Present, `clientData.type == webauthn.get` — because a signature check alone made "a Seal assertion" mean "any P-256 signature over these bytes", including one produced for a different relying party. **Ships in LOG-ONLY mode: `WebAuthnAssertion.enforceContextChecks = false`.** These checks have never run here, so nobody knows what the family's authenticators actually emit, and enforcing blind would un-verify real friendships with no way to tell an attack from a bad guess. Run a build, grep the `webauthn` os-log for CONTEXT VIOLATION over a few days, then flip the one line. UV is deliberately not required (`.preferred` keeps PIN-less keys tap-only per the 6/26 fix). (3) **`signReceipt` no longer signs caller-supplied bytes** — it takes the receipt's fields and builds the commitment itself. It was a root-key signing oracle: one careless caller away from a root signature over a `seal.backup.v1` or endorsement commitment, i.e. permanent takeover from a tap that looks like a handover receipt. Nothing was exploitable (the only caller was well-behaved) — the type system now guarantees what convention did. (4) **`seal.endorse.v3`**: the endorsement commitment length-frames both values (UInt32BE per field). v2 hashed `domain ‖ D ‖ K` with two variable-length values, so `(D, K)` and `(D‖K[0..<n], K[n...])` collided — one root signature authorising many splits, which let a REVOKED endorsement be re-split so it still verified while no longer byte-matching the revocation that killed it. **Migration window is OPEN: verification accepts v3 OR v2, creation is v3 only.** Every existing endorsement keeps working; a sign-in on each phone rewrites it as v3. Drop the v2 branch (`IdentityManager.legacyEndorsementCommitmentV2`) once every family phone has signed in on a v3 build. **Compat: an older build does not know v3, so a phone that re-endorses will not verify on one — the family updates together, as with wrapToAll and the backup-key authority set.** Item 5 (capping the security-key allow-list) is deliberately NOT done — capping trades a directory-flood DoS for a self-inflicted one; the reasoning and the real fix are in the plan doc.
