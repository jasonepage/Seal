## What Seal is
E2EE group chat where friendships require an in-person ceremony: friend taps THEIR FIDO2 hardware key (or passkey via hybrid flow) on YOUR phone; you verify their signature against the CloudKit public directory. Wedge: "everyone is provably human and provably someone you've met" (anti-bot/anti-AI positioning — see docs/VISION.md). Zero servers: CloudKit public DB + one static AASA file.

## Architecture (docs/SDS.md is authoritative)
- Root identity = WebAuthn credential (hardware key "Verified" tier = brass; passkey = silver). Root endorses per-device Secure Enclave P-256 signing key + software X25519 KEM key via assertion whose challenge commits to BOTH keys (`seal.endorse.v2` — binding auth+encryption keys, MITM fix).
- Messages: per-sender chains, HKDF ratchet, AES-GCM; AAD binds group|epoch|sender|index|prev-ciphertext-hash (transcript tamper evidence; epoch 0 = legacy `seal.msg.v2` format, epoch ≥1 = `v3`). Sender chains wrapped to members via X25519 ephemeral-static (ML-KEM hybrid still TODO, spike needed).
- Transport: CloudKit public DB, deterministic record names (no queries except GroupInvite): `msg.<group>[.e<epoch>].<sender>.<idx>`, `kenv.<group>[.e<epoch>].<sender>.<recipient>`. Push = CKQuerySubscription on Message.recipients.
- Groups: signed GroupInvite records (kind nil=invite, "update"=membership change); creator = admin; removal bumps epoch → fresh chains exclude removed member (FR-13 done).
- Revocation (FR-19 done): root-key assertion committing to device pub (`seal.revoke.v1`), stored in Identity.revocations; fetchIdentity filters revoked endorsements.
- Sign-in: assertion w/ empty allowList → directory lookup by credentialID hash → verify vs published pubkey → endorse this device (appended, multi-device-ish; senders wrap to `.last` endorsement). NOTE: security-key sign-in uses the directory's published credentialIDs as the allow-list (non-resident keys find nothing on an empty list). PIN'd-key "wrong PIN" was the `always_uv` vs `.discouraged` conflict — fixed 6/26 by switching to `.preferred` (see Known issues); residentKey stays `.discouraged` for this allow-list design.
- Storage: all local state keychain-JSON namespaced per identity hash (`seal.chats.<hash>` etc.); Sign out wipes local, identity survives in directory.

- Cross-device messaging — **WORKING / VERIFIED ON DEVICE 2026-06-29** ✅ (Nathan ↔ mom, two separate identities on two phones, current hardened build): registered, paired/scanned each other's seals (friend ceremony), and chatted both ways. The 6/26 desync hardening below is now CONFIRMED effective. ← History of the original bug retained below for context. Original DESYNC (found 6/26, first real two-identity test — Nathan ↔ mom): friending succeeded but messaging failed both ways — sender got "Sync failed: CryptoKit error 3" (KEM unwrap: peer wrapped to a KEM key this device no longer holds), receiver got "Dropped a message that failed verification" (message signed by a device key not in the peer's published+verified endorsements). Root cause = published endorsement ≠ keys actually in use (stale state from rebuild/reset churn; the clean same-build code path is internally consistent — first-message AAD/index/epoch verified symmetric). HARDENING SHIPPED 6/26 (CeremonyManager untouched; ChatEngine + HybridKEM):
  - Sender wraps the epoch key to **every** endorsed device KEM key, not just `.last` (`HybridKEM.wrapToAll`); receiver tries its key against each copy (`unwrap` now accepts an envelope ARRAY or a legacy single). **Compat: a new-build envelope (array) is unreadable by an OLD build — both phones must run this build.**
  - Receiver self-heals a stale directory cache: on a verify miss it refetches the sender's identity once (`directoryEntry(forceRefresh:)`) before dropping.
  - Sender self-heals its own publication: `ensureSelfPublished` (once per launch, in `refreshAll`) republishes this device's endorsement if it isn't in the directory's VERIFIED set.
  - Raw `CryptoKit error 3` / generic "failed verification" replaced with plain-language, actionable notices; new `messaging` os-log category (subsystem `io.github.jasonepage.Seal`) logs key FINGERPRINTS (8 hex) on send/unwrap-fail/verify-fail to pin any residual desync. **VERIFIED ON DEVICE 2026-06-29** — confirmed working on two phones on THIS build (Nathan ↔ mom, both directions). The `messaging` os-log + 8-hex fingerprint tracing stays in for future triage. Residual limit (unchanged, watch for it): if a phone's current key was NEVER published, the peer still can't reach it until that phone reopens the app (self-republish) or you re-friend.
- PIN'd security keys: "wrong PIN despite correct PIN" — **ROOT CAUSE FOUND 6/26.** Modern FIDO2.1 keys ship with `always_uv` enabled once a PIN is set, so they FORCE the CTAP2 clientPIN ceremony regardless of what the RP requests. Our `userVerificationPreference = .discouraged` therefore *conflicted* with the key (RP says "no UV", key insists "UV required"); iOS drove the PIN path in that contradictory state → bogus "wrong PIN" (same class as the iOS 18.1 FIDO PIN-loop bug Apple fixed in 18.2; Token2 saw it as a never-completing loop on Windows). The earlier "fixed by residentKey .discouraged" theory was wrong — residentKey is orthogonal to the PIN. **FIX (6/26):** switched all 4 security-key requests in CeremonyManager to `.preferred` — iOS now agrees with the key and the ceremony completes; pinless keys stay tap-only (.preferred prompts only if a PIN is set, per FIDO spec). residentKey stays `.discouraged` for the allow-list sign-in design. **UNVERIFIED ON DEVICE** — retest: PIN'd key over NFC *and* USB-C (5Ci); confirm pinless key + passkey/Face ID still work.
- Account deletion / tombstones HARDENED 6/26 (bug: deleted accounts could still sign in). Root cause: the tombstone was only a `tier="deleted"` flag on the Identity record, which the app republishes on sign-in, on every device refresh, and via the new `ensureSelfPublished` — and if the record was removed outright in the CloudKit console, `publishIdentity` just re-created a fresh LIVE one. FIX: deletion now also writes a WRITE-ONCE marker record `tomb.<hash>` (reuses the `Identity` record type — **no schema change**); `SyncEngine.isTombstoned()` checks it; `publishIdentity` refuses to publish a tombstoned identity, and sign-in throws the new `CeremonyError.identityDeleted`. So a deleted identity can't be revived by any republish path. NOTE: to retire the currently-stuck/revived accounts, sign into each on THIS build and use Profile → Delete identity (that now writes the permanent marker) — console-deleting the Identity record alone leaves no marker and can be republished. `fetchAllCredentialIDs` skips tombstones (tier filter + tomb records have no credentialID), so the same key can still re-register.
