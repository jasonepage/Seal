## 3. Why mom got no notification

### 3.1 Primary hypothesis — stale record collision silently eats the message

**Confidence in the mechanism: 0.9. Confidence that this is what happened to mom: 0.5** (needs
one log check to confirm — see §4).

**[FACT]** Message records use deterministic names: `msg.<group>.e<epoch>.<sender>.<index>`.

**[FACT]** The sender's chain index lives in the keychain at `seal.chains.<hash>`, and
`ChatEngine.wipe(ownerHash:)` (ChatEngine.swift:150–153) **deletes it on sign-out**. Index
resets to 0. The CloudKit records from the previous session do not reset.

**[FACT]** On a name collision, `send()` swallows it (ChatEngine.swift:634–639):

```swift
} catch let ckError as CKError where ckError.code == .serverRecordChanged {
    // ... It IS delivered — don't requeue or it loops.
    ChatEngine.msgLog.error("send: slot \(index) already exists — treating as delivered")
}
```

No record is written. The UI marks the message delivered.

**[FACT]** The push subscription fires on **creation only** — `options: .firesOnRecordCreation`
(SyncEngine.ensureMessageSubscription).

**[INFER]** Therefore: if your send chain was ever reset while the old server records survived,
every subsequent send collides → **no record created → no push fires → mom gets nothing —
while your phone shows the message as sent.** That is exactly the symptom you described.

**[FACT] It gets worse on the receiving side.** `refresh()` walks the sender's chain from its
own expected index. Inside the `while` loop, `AES.GCM.open` is *not* individually caught — a
throw escapes to the outer `catch`, which abandons that sender entirely. So a stale ciphertext
sitting at the expected index makes the receiver's chain **stall permanently**, on every
refresh, not just once.

**[INFER]** This is the same class of bug you fixed on Jun 29 for `saveKeyEnvelope` — you made
envelopes fetch-then-overwrite precisely because a re-keyed sender left stale state behind. The
fix was applied to the envelope path and **not** to the message path.

### 3.2 Confirmed defect — typing indicators send push notifications

**Confidence: 0.9.**

**[FACT]** `sendTyping`, `ackRead`, and `react` all route through `sendPayload` → `send()` →
`saveMessage`, which sets `recipients` and creates a real `Message` record.

**[FACT]** The subscription fires on *any* Message creation naming you as recipient, with the
static body "New sealed message."

**[INFER]** Every typing ping (throttled to 1 per 4 s) and every read receipt therefore pushes
a **"New sealed message"** banner to the other person. Mom may have been getting phantom
notifications for you typing, and — if she muted Seal because of that — real ones too.

This needs a `kind` filter or a separate non-alerting subscription for non-bubble kinds.

### 3.3 Confirmed defect — background remote-notification mode is missing

**Confidence: 0.95.**

**[FACT]** The subscriptions set `shouldSendContentAvailable = true`, but the target has
`GENERATE_INFOPLIST_FILE = YES`, no `Info.plist`, and **no `INFOPLIST_KEY_UIBackgroundModes`**.
Background Modes → Remote notifications was never enabled. Your own `docs/RETENTION.md:17`
flags this as a required manual step.

**[FACT]** Per Apple's documented behaviour, an alert push still displays without this
capability; only the silent background wake no-ops.

**[INFER]** So this is **not** the cause of a missing banner — but it does mean the app never
pre-fetches in the background, so messages only decrypt once she opens the app.

## 5. Recommended fixes, in order

1. **Stop the silent swallow (§3.1).** On `.serverRecordChanged`, don't claim delivery. Two
   viable designs:
   - *(a) Re-ratchet and retry into the next free index* — preserves "every message gets its
     own record," so creation fires the push. Needs re-encryption at the new index because the
     index is bound into the AAD.
   - *(b) Bump the epoch on sign-in / local wipe* — epoch rotation already exists (used for
     member removal) and gives everyone fresh record names and fresh chains. Simpler, blunter,
     and it fixes the receiver-stall too.

   **(b) is the smaller, safer change.** Recommend it.
2. **Don't stall the receiver.** Wrap the per-message `AES.GCM.open` in its own catch that
   advances past the bad slot — the code already does this for signature-verify misses
   (`Self.advance(&chain)`), just not for decrypt failures.
3. **Stop typing indicators from pushing (§3.2).** Either add a `kind` field to the Message
   record so the subscription predicate can exclude non-bubble kinds, or route
   typing/read/reaction through a second subscription with no alert.
4. **Enable Remote notifications background mode (§3.3).**
5. **Re-deploy the CloudKit schema to Production** before the next TestFlight build.
6. **Then** retest with two phones, app fully closed, and finally record the FR-24 demo video —
   the last real submission blocker.
